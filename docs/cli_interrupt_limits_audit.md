# 现场 CLI 中断条件清单：哪些删除，哪些改行为

审计日期：2026-11-12。已实施A03起点重规划、A06/A07接收超时2秒/3秒，以及A08速度默认1.5rad/s/位置只记录、A09/A10删除跟踪与老化跟踪门禁，以及A14/A15删除正常结束的回位验收、P07允许现场单程参考。现场数据质量和批次推进门禁现也按用户决定删除，见第4–6节；其余建议未实施。

## 先看结论

你担心的情形确实存在：GUI 的“限制设置”只作用于新手动控制，**不会修改 `hardware-snapshot`、`hardware-execute`、`hardware-run-batch` 的规则**。H1–H4 仍有写死阈值、较短等待期限，以及将数据质量错误归类成整批故障的行为。

我建议优先处理下面五类，而不是统一删除所有 limit：

1. **删除现场操作的硬编码**：启动的 `0.02 rad/s`（回位门禁已删除）、启动 10 秒、单轴 jog 最大 5°、发送频率仅三档、PD/前馈的通用数值封顶。改成显式现场配置；不是用无限大常数代替。
2. **改变等待行为**：启动时尚未静止、未发现反馈/服务，应显示根因并等待或取消。起姿变化应要求重新建立参考，不直接结束整个批次。
3. **把数据质量与执行故障分开**：匀速平台、周期窗口、静态窗口、拟合残差不合格，保留数据、给出拒绝原因和重采选择；不要因分析抛异常就给整个批次盖上“设备故障、禁止续采”。
4. **统一可调运行策略**：速度、回调超时等集中列出实际值及触发动作；位置越界已改只记录，跟踪偏差门禁已删除。失去有效反馈、模式或控制所有权时仍结束发送。
5. **正式结果门槛留在分析/验收**：采样、尺度、物理一致性、留出误差等决定“能否认可结果”，不应伪装成电机保护，也不能靠删除检查把不合格数据写成标定通过。

下面的编号可直接用于逐项决策，例如“取消 P01 的 5°封顶，A01 改等待，Q04 改可重采”。“建议”均为待决定事项。

## 怎样读这份清单

主要范围是你线下会实际调用的路径：

- `fieldwork/run.sh preflight / observe / reconnect`：只读 CLI。
- `hardware-snapshot / hardware-plan-jog / hardware-plan-static / hardware-execute / hardware-analyse`：H1。
- `hardware-plan-batch / hardware-run-batch / hardware-analyse-batch`：H2–H4。
- GUI、Mock、S3/S4/P0 另列，避免把别的入口规则当成实机 CLI 的保护。

**四种后果必须区分：**拒绝规划/启动、运行中停止发布、批次停止推进、分析/验收拒绝。CLI 返回非零也不必然意味着机器人运行中被停发。

表内默认值取根目录 `configs/hardware_field.yaml`、`hardware_batch.yaml`、`hardware_friction.yaml`、`hardware_inertia.yaml`；已封存批次使用其自身 `protocol` 中的值。修改源 YAML 不改变旧批次；当前实现/SDK改变后旧批次也不能直接续采。

“可配”指现有 YAML 或参数可改，不等于命令行已有覆盖选项；目前多数没有便捷的 CLI 覆盖入口。
