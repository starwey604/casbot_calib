# 2026-11-14 SSH会话中断：发送器退出、失能并可重新只读连接

用户授权代理执行SSH断线试验。本轮先做只读，再做一次15秒上限的C01保持；分别关闭测试SSH连接，未断开用户会话、拔网线或中断EtherCAT总线。用户对保持断线后的观察为：**“已松软下垂。”**

## 结果

| 用例 | 原生记录与后续连接 | 结论 |
| --- | --- | --- |
| 只读连接关闭 | 原定20秒，约12.07秒时中断；`reason=operator_interrupt`，0命令；观测进程已退出。后续两秒只读2000行主站反馈、0命令 | 本次SSH/PTTY关闭结束了只读owner，重新连接正常 |
| 保持阶段关闭 | C01上限15秒、Kp20/Kd2、前馈0；进入保持约1.08181秒时中断。`reason=operator_interrupt`、`disable_ack=1`；退出段7条成功命令，双臂控制字0x06，末反馈状态0x21 | 本次连接关闭触发受控退出，原生发送器收到失能应答；用户观察松软下垂 |
| 保持断线后重新连接 | 两秒只读2000行帧号各不相同的主站反馈、0命令，双臂状态均为0x21 | 连接资源已释放；未重握手、清队列、重新使能或续旧控制 |

本轮所记录电机槽0–28错误码均为0。没有使用备用SIGTERM恢复命令；发送器已退出，主站保持运行，试验结束时没有活动控制进程。上述主站帧数不作为独立电机采样次数。

## 测的是什么连接

- 实机源码版本`79d694b`，同一开机窗口`d4d463d3-a56d-4885-8858-7b313ed12fd5`。
- 两条测试连接均使用独立OpenSSH TCP连接，关闭复用（ControlMaster=no、ControlPath=none），分配PTY；没有tmux/nohup。
- 保留另一条独立管理连接，提前记录目标PID/启动时刻及可单独调用的检查/TERM恢复入口。恢复入口只允许当前用例、相同PID启动时刻及匹配输出目录的发送器；本轮未调用其发送信号功能。
- 在观测/保持已经开始后，用OpenSSH的换行`~.`关闭相应测试连接。三条连接的SSH_CONNECTION四元组不同，见证据目录元数据。
- 本次不是拔网线、静默丢包或TCP长时间未发现故障，也不覆盖tmux/nohup、无PTY后台控制或SIGKILL。

本次松软的路径是：SSH/PTTY关闭 → 发送器进入中断退出 → 显式发失能 → 收到应答。此前C05三秒停写仍保持使能，两者机制不同。不能依赖SSH网络状态替代GUI活动控制的显式停止/进程监督。

## 发现并修复外层报告收尾问题

两条真实SSH断开用例的原生命令/反馈及`result.txt`完整，`process.json`也已保存退出码/结束时刻，但外层CLI未生成最终报告。已用离线report恢复报告；保持用例登记了用户“已松软下垂”的原话。没有修改原始进程元数据或补造具体信号来源。

私有重复SIGHUP可复现收尾被中断；另一个在离线报告阶段发送HUP的用例复现“退出元数据已保存、最终报告缺失”，与本次记录一致。历史SSH关闭时的具体信号顺序没有单独记录。现修改CLI监督收尾：

- 首次中断进入一次退出流程，重复挂断不再次打断清理；
- 原生子进程退出结果与外层结束元数据先落盘；
- 原生子进程退出后，离线报告写完前保护整个HUP窗口，整个用例结束后恢复调用方的处理方式。

单次HUP、重复HUP、关闭PTY及报告阶段HUP四项私有回归通过，相关C06及监督超时回归也通过。修复只涉及Python收尾；没有再次运行实机保持来验证新版本，也没有改变C++失能状态机。
