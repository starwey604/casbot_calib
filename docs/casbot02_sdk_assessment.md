## 结论与适用范围

文档确认二次开发使用ROS 2 topic/service/action，符合项目已有ROS接入方向。现有Pinocchio动力学/运动学、Coal碰撞、辨识和只读回放算法可以复用，需补齐厂商消息映射、真实时间采集后端、设备能力声明、模式与控制权管理。

文档明确描述上身关节位置控制；力矩/电流命令、混合PD、前馈及增益配置、原始电流、高频采样和采用回执尚未确认。因此，TriCal低速对点采集与公开接口较匹配，完整动力学流程仍依赖甲方补充接口与观测条件。ROS连通、位置运动可用和动力学实验条件满足应分别验收。

文档没有说明底层是否使用ros2_control。先对接甲方已开放的ROS接口，若甲方已有控制器/hardware_interface则复用；不以自行新增ros2_control硬件插件作为接入前提，不另起重复硬件控制循环。

| 上身位置控制 | `/upper_body_debug/joint_cmd` | `crb_ros_msg/msg/UpperJointData` | 第23–24页；支持单帧、离散多帧、连续帧位置控制 |
| 通用关节反馈 | `/joint_states` | `sensor_msgs/msg/JointState` | 第13页；描述位置、速度、力矩，实际字段有效性及来源待确认 |
| 申请/退出全身调试 | `/motion/whole_body_debug` | `std_srvs/srv/SetBool` | 第24页；全身控制路径，不能默认与上身模式等价 |
| 运动模式反馈 | `/motion/current_mode` | `std_msgs/msg/Int32` | 第25页图片；阻尼1、准备2、全身调试7、上身调试8 |

`UpperJointData`包含`std_msgs/Header header`、`float32 time_ref`、`float32 vel_scale`及`sensor_msgs/JointState joint`。文档将`time_ref`标为执行时间、单位秒，`vel_scale`范围为[0,1]，但没有解释时间基准、覆盖/排队、插值或两者的组合规则。第23页接口定义同时写有“通讯方式：ros2 service”和topic名称/消息类型，本文按topic描述记录，仍需以正式接口包及甲方说明核对。

`JointState.effort`字段存在，不证明它可以作为力矩命令，也不证明反馈是独立测力。第8页的50Hz动作data文件属于技能播放路径；旧版无相邻帧插值的说明针对该路径，不能外推到上身连续topic，也不能用技能播放替代当前动态采集后端。

## 当前实现的接入缺口

### 1. 双臂采集仍与Mock执行绑定

- [staged_collection.py](../python/casbot_calib/staged_collection.py)构造`ArmSimulationConfig`并直接调用`ArmSimulationRunner`或`run_guarded_arm`；[staged_workflow.py](../python/casbot_calib/staged_workflow.py)也直接构造合成设备。现有分阶段命令并非可直接切换到实机的入口。
- [trical_device.py](../python/casbot_calib/trical_device.py)提供`MockDevice`；[trical_workflow.py](../python/casbot_calib/trical_workflow.py)通过`submit()`、`advance()`及虚拟时间分块推进运动，还从配置home初始化命令姿态。实机需先读取实际姿态，再规划起始保持和接近路径。
- [simulator.hpp](../cpp/include/casbot_calib/simulator.hpp)已有单关节`JointDevice`读写边界；双臂侧的[arm_simulator.hpp](../cpp/include/casbot_calib/arm_simulator.hpp)主要是模拟命令、样本及会话，仍需补充具名14轴设备后端边界。

建议将命令发送、观测接收、能力查询、模式管理和停止抽为可替换后端。Mock保留持久化`ArmSimulationSession`及虚拟推进；真实设备使用真实时间和异步反馈，不实现虚拟时间推进。TriCal的三表输入单独适配，保留各表和关节的独立时间/状态。

厂商适配建议作为可选ament包依赖正式`crb_ros_msg`、标准消息和服务包；核心算法及离线分析不增加厂商ROS包强制依赖。当前自定义[ROS消息](../ros/casbot_calib_interfaces/msg/JointCommand.msg)需要语义转换，不能仅靠topic重映射接入。

### 2. 需要纯位置模式及明确的能力门禁

[simulator.hpp](../cpp/include/casbot_calib/simulator.hpp)的`Mode`只有torque/mixed_pd，`DeviceCapabilities`默认位置、速度、电流、力矩命令及混合PD可用；当前ROS `JointCommand`同样只有TORQUE/POSITION_PD。厂商适配不能直接继承这些Mock能力默认值。

建议增加纯位置控制表达；真实设备能力区分已确认支持、已确认不支持和未知，阶段开始前检查必要条件。缺失的前馈、Kp/Kd不能静默丢弃后仍按原控制实验验收。

| 工作 | 文档能支持的判断 | 开放实验前的条件 |
| --- | --- | --- |
| TriCal接近、对中、稳定采样 | 位置接口方向匹配 | 实际模型/工具/夹具、真实三表、有效关节反馈、运动与停止语义确认；不代表几何辨识已完成 |
| 重力辨识 | 位置接口可提供姿态激励 | 可信的电流/力矩观测、尺度锚点、静态稳定与批次条件 |
| 运动摩擦、惯量辨识 | 位置接口可提供运动激励 | 实际轨迹/时序、反馈来源与带宽、有效采样、饱和与滤波信息及独立验证 |
| 当前起动摩擦力矩斜坡 | 尚无已确认命令能力 | 力矩/电流命令、补偿与保护能力；不能直接以位置运动替代当前方法 |
| 固定PD下前馈及调PD对照 | 尚无已确认控制能力 | 前馈与增益接口、控制器行为和限制可追溯 |

### 3. 关节顺序、选装配置和腕部限位存在待核对项

第3页腕部按yaw→roll→pitch列出，第23页控制关节表按yaw→pitch→roll列出；当前模型采用yaw→pitch→roll链。适配应按关节名称映射并检查缺失、重复及数组长度，不把文档表格行号当作设备数组顺序。第3页将部分腕轴标为选装，而项目当前固定为7+7轴，需确认实际交付配置。

第3页与[当前nominal URDF](../python/casbot_calib/assets/casbot_dual_arm_benchmark_nominal.urdf)的roll限位如下，单位rad：

| 关节 | 开发文档 | 当前URDF |
| --- | --- | --- |
| `left_wrist_roll_joint` | [-1.0472, 1.5708] | [-1.5708, 1.0472] |
| `right_wrist_roll_joint` | [-1.5708, 1.0472] | 约[-1.0472, 1.5708] |

这是资料冲突，尚不能判断哪份对应实机；可能涉及型号、版本或方向约定，不能仅凭该表直接修改模型。第1页明确URDF需联系销售获取。需取得对应实机的URDF、关节方向/机械零位和限制配置，与当前20251015 nominal模型逐项核验，避免与evt6混用。模型或几何确认变更后，更新身份摘要和碰撞缓存，重验规划、过渡、停止及相关动力学结果；真实工具负载、腰部固定变换和重力方向另行测量。

### 4. 反馈需要字段有效性、来源和时钟声明

文档未解释effort来源、原始电流、速度生成方式、时间戳语义、采样频率、电流滤波/带宽、饱和及故障状态。`/joint_states`与`/motion/joint_state`是否同源、同频、同延迟也待确认，不能默认合并。

[staged_identification.py](../python/casbot_calib/staged_identification.py)目前要求完整14轴q/dq/current/status、连续序号、均匀整数纳秒采样，并使用`current × gain`形成力矩观测。这些是当前采集契约，不能通过给缺失字段填零、伪造设备序号或采样时刻来满足。

建议保留厂商原始消息、header及本地主机单调接收时刻，另做规范化记录。字段增加可用性、单位和来源；effort按已核实来源处理，不能直接改名为电流或在未知增益下反推。时间统一使用整数纳秒，未知采样时间及未知时钟映射显式记录；本地接收序号仅说明接收顺序，不证明设备采样连续性。

静态TriCal可在已验证的延迟界和稳定窗口条件下使用异步观测，不能据此声称同步。动态数据需在连续有效片段内处理非均匀采样，处理结果另存且关联原始记录，不跨缺帧求导，不将接收时间直接当采样时间。若拿不到主机写入历史/采样时刻，不能套用M2驱动拟合声称分离了网络、控制等待和驱动响应。

### 5. 模式、控制权、执行与停止需要状态机

建议流程为：只读观测与身份核对→读取实际起始姿态→检查完整路径及停止条件→申请上身调试→检查服务结果并确认模式反馈→执行→按已确认策略停止/退出。执行中持续检查模式、控制权、关节反馈新鲜度、限制及碰撞条件。

上身接口覆盖头、腰、双臂和手，需确认能否只发送14轴子集、未指定关节如何保持。腰部刚性固定工况下不应默认为全身调试，也不能因SDK要求整组消息就用零值填充其他关节。

`SetBool(false)`只被文档定义为退出调试，不能视为已确认的抱持、制动或急停。当前Mock失联后的名义重力加弱阻尼回退、TriCal故障撤离和回home策略均不能直接当实机停止策略。模式丢失、陈旧反馈、断流和人工接管后，应按已确认设备能力处理；停止和恢复路径仍需门禁。

### 6. 实机预检入口与本机Mock基准保持独立

[ros_benchmark.py](../python/casbot_calib/ros_benchmark.py)限定`scope: localhost_ros_mock`，设置`ROS_LOCALHOST_ONLY=1`、随机domain和私有命名空间，应保留该隔离。实机使用独立入口，显式配置目标topic、ROS domain、RMW/DDS、网卡及QoS，避免改动现有基准后误启动真实命令。

文档未承诺500Hz命令，也未承诺4kHz/8kHz原始电流记录。需分别测命令发送、主机采用、原始采样、反馈发布和接收，未知量保持未知。500Hz topic瞬时电流不能自动替代高带宽原始记录；可向甲方争取主机记录、批量回传或独立验证的周期平均观测。当前合成门槛及本机回环结果不作为物理以太网或硬实时验收。

## 建议实施顺序与检查

以下均为待实施建议，本文本身不新增可运行的SDK后端。

1. **只读记录与能力配置**：收到正式接口包后，记录模式和选定关节反馈，保留原始数据、版本、时钟和来源。离线检查名称乱序、缺轴/重复、空字段、未知时间、反馈中断等输入；未满足能力条件的阶段应被拒绝。
2. **抽取后端并保留Mock回归**：分开虚拟推进和真实时间调度，复用现有轨迹/门禁/分析；验证没有前馈能力时不会静默执行原前馈实验。新会话使用新schema/目录，不改写旧数据。
3. **上身位置控制与TriCal薄适配**：模型、初始姿态、子集语义、控制权及停止能力确认后，按任务授权开展实机预检。验证模式失败/丢失、陈旧观测、断流及停止路径；三表各自的通信、行程、时间和真实载荷单独接入。K2测量闭环不等于K3几何求解或实机精度验收。
4. **按能力开放动力学阶段**：确认尺度、观测带宽和实际时序后，依次推进重力→运动摩擦→起动摩擦→惯量→独立验证→控制对照。前序验收失败阻止后续，独立轨迹和冻结参数要求保持不变。
