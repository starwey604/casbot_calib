# nice!nano 三表并发实测（2026-11-20）

同一块 nice!nano（USB 序列号 `D0682ED4F93F8620`）同时连接了三块广陆表。三轮各 60 秒的轮询中，三表均持续订阅，连接轮次未变，均收到有效 `DAT0`。三表可按每表 5 Hz（200 ms）轮询；本次每表实际收到 2.72–3.45 条/秒。

## 自动连接固件：三闪后逐表读数

刷入自动连接固件后关闭串口，逐块唤醒三块表，全程未发送连接命令。板灯三闪时重新打开串口，`status` 返回 `ready_count=3`；逐槽发送 `MEAS`，三块表均返回数值：

| 本次槽位 | 表 | 蓝牙地址（public） | 原始通知 |
| --- | --- | --- | --- |
| 0 | A | `78:CD:55:45:64:04` | `DAT0:m+0.00` |
| 1 | C | `78:CD:55:45:67:AD` | `DAT0:m+0.000` |
| 2 | B | `78:CD:55:45:6A:6B` | `DAT0:m+0.000` |

再次关闭并重开串口，三槽仍为 `ready`，地址不变，连接轮次仍为 `[1,1,1]`。原始记录：`artifacts/qas_auto_20261120_162925/events.jsonl`。日常操作见[USB 读写指南](../../firmware/docs/qas_usb.md)。

## 早期手动连接固件：排查第三块加入时的掉线

先让液晶显示数值，再逐表唤醒发射器。把本次逐一识别的实物记为 A、B、C（不指定轴向）。按地址连接、订阅成功并收到数值后，再确认下一块。等第三块时先前的表曾断开；此时应以板端槽位状态和广播为准，只唤醒缺席的表。

对照中，A、C 已在线，尝试加入尚未确认广播的 B 失败，但 A、C 没掉线：约 30 秒内各收到 60 条读数。随后确认 B 已广播、A 和 C 仍为 ready，同一次加入就使三槽同时 ready。这排除了这套板卡与仪表只能连两块的解释。

回看第一次组网，A 的断线事件比主机第一次请求连接 C 早 24.7 秒。组网期间的六次已建立链路断开均报 HCI `0x13`（对端终止连接），没有主机发出的 USB `disconnect` 命令。与记录更吻合的是，等下一块表进入广播期间，有的发射器已先行退出连接。是否由按键或仪表空闲策略触发，现有日志分不出。

## 连接数指示灯上板复测

刷入带连接数指示灯的修订固件后，按 A → C → B 逐块接入。现场看到第一块接入后单闪，第三块接入后三闪。B 加入前，A、C 的槽位均为 `ready`；B 加入后，三槽均为 `ready`，逐表请求均收到了有效 `DAT0`。从第一块接入到三表回读结束，没有断开或重连，未复现第三块加入时原有连接掉线的现象。原始记录：`artifacts/qas_led_retest_20261120_160952/events.jsonl`。

## 同一组三条连接的三轮对照

主机交错发送 `MEAS`（wcmd），三表均回读 `MOD:0`。以板端接收时刻划定 60 秒窗口，统计实际数值通知，保留重复值，不计 `MEAS:OK`。最长间隔是同一表相邻两条有效通知的接收时间差。

| 表 / 槽 / 蓝牙地址（public） | 4 Hz：条数 / 条每秒 / 最长间隔 | 5 Hz：条数 / 条每秒 / 最长间隔 | 8 Hz：条数 / 条每秒 / 最长间隔 |
| --- | --- | --- | --- |
| A / 0 / `78:CD:55:45:64:04` | 203 / 3.38 / 1.56 s | 207 / 3.45 / 1.04 s | 206 / 3.43 / 1.56 s |
| B / 1 / `78:CD:55:45:6A:6B` | 159 / 2.65 / 1.94 s | 163 / 2.72 / 1.77 s | 164 / 2.73 / 2.45 s |
| C / 2 / `78:CD:55:45:67:AD` | 198 / 3.30 / 1.56 s | 200 / 3.33 / 1.05 s | 204 / 3.40 / 1.82 s |

按 4、5、8 Hz 请求时，三表合计分别收到 560、570、574 条有效读数；因前一笔写入未完成返回 busy 的次数分别为 30、79、235。5 Hz 档每表尝试 300 次，A、B、C 实际提交 271、276、274 次。三档各表的通知间隔中位数均约 255 ms，板端事件和 USB 队列损失计数均未增加。标定采集应保留每块表各自的接收时间；三条链路在线不等于三表同时采样。
